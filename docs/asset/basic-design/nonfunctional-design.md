## 3. セキュリティ設計（対応：NFR-04〜NFR-09・NFR-14）

### 3.1 認証分離（NFR-04）

4 種類の認証境界 A1〜A4 の混用禁止と、A3（Integration Guard：受信 Bearer token を env `INTEGRATION_TOKEN` と**定数時間比較**で検証・静的 Bearer Token は EC 認証パラメータ `guardSecret`（既存・新規追加なし・2026-09-02 S-2 時存入値）＋カスタムヘッダー注入・NC 数式許可 ON・C-2 修订 2026-09-03）の設計は BD-01 §4 に譲る（本書では重複記載しない）。A1 の Redis ブラックリスト（ログアウト・無効化・リフレッシュ失効）とロールの DB 毎回参照は既存実装（`src/common/guards/jwt-auth.guard.ts` 実測・✅）。A2/A3 は ✅ 実装済（A2=3d88923・A3=6ab01c9/8581f50・2026-09-03/09-04）。検証は MV-11（誤 token／欠落 token で 401/403）。

### 3.2 サービス認証とユーザー認証の分離原則（NFR-04・REQ-029）

「どのシステムが API を呼べるか」（A2/A3）と「誰がコマンドを提出できるか」（A1/A4）を分離する。Booking 側受入エンドポイントは JWT ガードを迂回した匿名端点とせず、Integration Guard で独立に保護する（✅ 実装済・6ab01c9/8581f50・2026-09-03）。

### 3.3 認可・最終裁定（NFR-05）

ロール（CUSTOMER/ADMIN）ごとにサーバ側が最終裁定する。フロント三層（middleware・AuthGuard＋routePermissions・コンポーネント判定）は UX 制御でありセキュリティ境界ではない（BD-04 §3.3・実測✅）。バックエンド `JwtAuthGuard`（APP_GUARD グローバル）＋`RolesGuard`／`AdminGuard` が最終裁定（✅）。顧客 JWT での管理系 API 呼出は 403（MV-01 後半・NFR-05 検証方法）。

### 3.4 行級限定・最小権限（NFR-06・REQ-030・RULE-13）

`Booking__c`／`Booking_Command__c` は External OWD=Private＋Sharing Set（Account 隔離）とし、外部ユーザーは自 Account のレコードのみ CRUD/FLS の範囲で操作する。Apex は with sharing。権限マトリクス（F-32）は 🔵 P0-2 で契約凍結、Apex／LWC 実装は 🔵 P0-3/P0-4 計画。検証は MV-07（他 Account のレコード ID 直指定でアクセス拒否）。

### 3.5 操作者のサーバ側確定（NFR-06 関連・RULE-12）

コマンド要求者は静的マッピング（`salesforceUserId ↔ bookingUserId`・active 1 件）でサーバ側確定し、ブラウザ申告 ID は採用しない。マッピング不存在／inactive・非 ADMIN/ACTIVE は拒否（✅ 実装済・8581f50・2026-09-03）。

### 3.6 監査ログ（NFR-07・REQ-031）

| 種別 | 記録先・項目 | 状態 |

注：`AppointmentHistory` は実装上の書込み経路が存在しないため連携監査には用いない（BD-07 §4.2・RD-01 REQ-031 備考と一致）。アプリログには PII を平文出力しない方針とする（現状の既知盲点＝`bookings.service.ts:243` の電話番号ログ出力は 2026-09-01 に P0-2 契約内で是正済み・マスキング適用・BD-07 §5 に既録）。

### 3.7 暗号化・通信・データ最小化（NFR-08・NFR-14・RULE-11）

- 全通信を HTTPS とする（Salesforce 側は強制・Booking 側はローカル開発では HTTP のまま、外部公開時は TLS 終端を要する＝**デモ構成の限界を正直に記載**）。
- JWT は HttpOnly Cookie で輸送（✅・A1）。
- PII 5 項目（氏名・電話・メール・WeChat・備考・TERM-29）は投影ペイロード・`Booking__c` のいずれにも出現させない。ホワイトリスト（RULE-11・契約凍結）による構造的除外であり、運用注意ではなく設計で担保する（🔵 P0-3）→✅ 実装済（§8 参照・3d88923）。検証：投影レコード項目の目視照合＋Apex テストのアサーション（MV-04 併せて）。
- 個人情報の目的外提供禁止（NFR-14）：投影ホワイトリスト運用で担保し、Salesforce 標準セキュリティ機能（OWD・Sharing Set・CRUD/FLS）の範囲内で実装する。

## 4. 可用性設計（対応：NFR-10）

- **単一構成・冗長なし**：PostgreSQL・Redis・Booking API・フロントエンドは単一インスタンス、Salesforce は単一開発組織（BD-01 §3.7・✅）。
- 可用性率・RTO/RPO の数値目標を**設定しない**。設定しない理由：本件はデモ級の単一構成であり、冗長化・フェイルオーバーの設計が存在しないため、数値目標は検証不可能な虚数となる（RD-02 NFR-10 と同一口径）。
- 障害時復旧：手動再起動（`compose restart`）で復旧する（✅ 運用手順・検証 1 回実施が RD-02 の検証方法）。
- コマンド側の縮退：Booking 停止時はコマンドが QUEUED／リトライ状態で滞留し、復旧後に Queueable 再実行・手動 Retry で回収する（P0 の限界・Outbox/Worker なし＝REQ-037）。

## 5. 運用設計（対応：NFR-11）

### 5.1 周期ジョブ（retention・✅ 既存実装）

| 項目 | 実測値（`src/modules/retention/` 実測） |
|---|---|
| スケジュール | cron 既定 `0 30 2 * * *`＝**毎日 02:30**（`RETENTION_CRON` で変更可・RetentionScheduler 実測） |

| 運用確認 | デモ期間中は月 1 回、削除ログ／件数を目視確認（NFR-11・BIZ-16） |

### 5.2 ログ・監視

- アプリログ（NestJS Logger）＋`ActivityLog`／`SystemLog` モデル（✅）。ログローテーション等の本番級設定は**未整備**である（デモ構成の正直な記載）。
- 連携監査の確認：`syncStatus=ERROR`・コマンド終状態（CONFLICT/FAILED）を目視確認し、手動 Retry の判断を行う（BIZ-15）。自動告警は設けない（REQ-037・P1）。

## 6. データ保全（対応：NFR-11 保持面・NFR-14）

- 永続化：PostgreSQL データは Docker ボリュームで永続化（✅・`booking-deploy` compose 実測）。
- **バックアップ運転は未整備である**（正直な記載）：世代管理・リストア手順・リストアリハーサルは本件に存在しない。デモデータは手動投入可能なため、消失時は再投入で回復する運用（NFR-12 の移行なし方針と整合）。
- 保持ポリシー：30 日ハードデリート（§5.1）。投影レコード（`Booking__c`）は正本クリーンアップ対象外・削除済み予約への遅延コマンドは 404/409 で判定可能（G7・REQ-033・🔵）。
- 削除は原則物理削除・論理削除フラグなし（BD-07 §4.4・✅ 実測）。個人情報は保持期限到来により消去される（NFR-14 の目的外保持防止に寄与）。

## 7. 拡張性・保守性（対応：NFR-13）

- P0 のスキーマ増分は `version`・`syncStatus` の 2 項目のみとし、P1 の Outbox／Worker 方式への置換時に破壊的変更を伴わない設計とする（NFR-13・BD-07 §2.2 計画増分）。検証：migration 差分レビュー（増分が version/syncStatus に限定されていること）。
- P1 フック（本書での将来接続点の記録・実装は行わない）：Outbox/Worker/DLQ／周期照合（REQ-037）・動的 provisioning（`SalesforceUserLink`・`sfAccessStatus`・REQ-038）・容量値マスタ化（RULE-06）・手動 Retry UI（REQ-028）。
- 設定外部化：環境変数（`RETENTION_*`・`CSRF_ENABLED`・JWT secret 等）による既存の設定外部化（✅）を踏襲する。連携新規設定（OAuth 秘密鍵・Named Credential secret・リトライ上限）も P0-3 で環境変数／secret 管理に置く方針（🔵）。
- 共通化：認証・エラー応答・ログ等の横断処理は BD-11『共通機能設計』（CF-xx）に集約し、各機能設計は差分のみ記載する。
